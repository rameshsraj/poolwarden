poolwarden: a command center for pgpool-II

One binary in one terminal for one pgpool cluster. See it, understand it, change it safely, and keep a record of who did what.

Go, pgpool-II 4.4/4.5, PostgreSQL 14 and later. Source: github.com/rameshsraj/poolwarden

Anyone who has run PostgreSQL behind pgpool-II with streaming replication knows the routine when something looks wrong. You open a few terminals. In one you run psql -p 9999 and SHOW POOL_NODES. In another, pcp_watchdog_info. Then you log into each backend to check pg_is_in_recovery() and pg_stat_replication, and you tail logs on whichever host you suspect. After all that you still have to reconcile the pieces in your head before deciding whether to run pcp_promote_node, and hope you typed the right node id.

I wrote poolwarden because I wanted a tool for exactly that moment. It is a single static Go binary that a DBA runs over SSH on a pgpool host. It is not a proxy, not an agent and not a daemon. It is a thin layer over the interfaces that pgpool and PostgreSQL already expose, and it adds the checks, confirmations and record keeping that those interfaces do not have.

Why another tool

pgpool-II does its own job well: pooling, load balancing, health checks, automatic failover and watchdog managed virtual IPs. What it leaves to the operator is the operating part, and in my experience that comes down to four recurring problems.

Several sources of truth that disagree

SHOW POOL_NODES tells you what pgpool believes. Each PostgreSQL node knows what it actually is. The watchdog knows who holds the VIP. These drift apart at the worst possible time, and nothing correlates them for you.

Powerful commands with no seat belt

pcp_promote_node, pcp_detach_node and pcp_recovery_node run immediately. There is no check that the standby is caught up, no confirmation, no verification afterwards and no record of who ran it.

Configuration by hand on every host

pgpool.conf, pool_hba.conf, pcp.conf and pool_passwd have to be identical on every pgpool host. Editing them by hand means drift, and you usually discover the drift during the next failover.

A shared account and scattered logs

Everyone logs in as postgres, so the question "who restarted pgpool at 02:14?" has no answer. pgpool and PostgreSQL logs live on different hosts in different formats.

poolwarden goes after each of these: cross checked views, guarded control commands, configuration changes as transactions, and an audit log that can tell people apart.

Where it sits

The first thing to understand is what poolwarden is not. It does not sit in the client traffic path, it never talks to application clients, and it never goes around pgpool to control PostgreSQL. If you delete the binary, the cluster keeps running exactly as before.

The tool adds the checklist before and the verification after. The action itself belongs to pgpool.

Architecture

Inside, poolwarden is a layered pipeline. Everything the user sees, whether a table, a finding or a plan, is derived from a single immutable Snapshot. One component builds it and every other component reads it.

The collector and the Snapshot

Every command starts the same way. The collector fans out to all sources in parallel, each with its own deadline (3 seconds by default), and assembles whatever came back into a Snapshot. A source that times out is recorded as UNREACHABLE and does not hold up the others, so a dead backend costs you three seconds rather than a hung terminal. The snapshot also keeps the provenance of each fact. That is what lets a view say "pgpool says up, direct connection says refused" instead of quietly picking one side.

One collection, many consumers. Degraded mode takes over when pgpool itself cannot answer SQL, which is usually the moment you most need to see the cluster.

Degraded mode is worth a few words. The classic pgpool outage is "all children busy": pgpool is alive but psql -p 9999 hangs forever. poolwarden notices the hang, takes node state from pcp_node_info and backend state from direct connections instead, and marks the output DEGRADED. You still get a picture of the cluster, along with a finding that explains why it is partial.

Diagnosis: findings with evidence and a next step

The diagnosis engine is a catalogue of 29 rules. Each one is a pure function with the signature func(Snapshot, History, Config) []Finding. There is no I/O in them, which makes them easy to table test. Each finding carries a severity, the subject it applies to, the evidence that fired it, the likely cause, and the exact next command to run.

explain <FINDING_ID> expands a finding into evidence, cause and fix. errors merges pgpool log errors, PostgreSQL log errors, connection failures and health check failures from every host into one time ordered stream. logs tails all of the logs together and classifies each line (FAILOVER, WATCHDOG, HEALTHCHECK and so on).

Forecasting

The collector writes every snapshot into a 24 hour on-disk ring. forecast fits a linear regression over the last five minutes of lag, retained WAL and busy children, and reports the slope, R² and an ETA to the critical threshold. It only prints an ETA when R² is at least 0.6; a noisy series is reported as unstable rather than given a made up number. The same trends feed the rising lag rule and the per node health score you see in status.

Guarded node control

Every control command, meaning promote, detach, attach, recover and reload, goes through the same five phases. Every phase is timed and written to the audit log.

Pre-flight, plan, confirm, execute, verify. Refusals and aborts are recorded the same way as successes.

The pre-flight checklist depends on the action. For a switchover, poolwarden checks that the target is a standby and up, that its replay delay is under the warning threshold, that it has the most advanced LSN of all the standbys, that watchdog quorum exists, that failover_command and follow_primary_command are set, that there is no split brain, and that no other failover is already in progress. detach warns you when the target is the primary, because detaching the primary triggers a failover, and tells you how much load balancing capacity you are about to lose. attach refuses a node that is on a different timeline from the primary, which is the classic way to attach a stale node and serve wrong reads.

The output is a timeline rather than a spinner:

$ poolwarden promote 0 --ticket TB-1
STEP                         START     END       DURATION  RESULT
preflight                    05:28:25  05:28:25  0.1s      ok
pcp_promote_node             05:28:25  05:28:25  0.0s      ok
verify                       05:28:25  05:28:27  2s        ok
verify (old primary rejoin)  05:28:27  05:28:28  0.1s
outcome: success  event: d3c47530ebb20ec0

The second verify step is there on purpose. A switchover is not done when the new primary accepts writes. It is done when the old primary has been re-pointed by follow_primary_command and is streaming again. poolwarden waits for that as well, and if the old primary does not come back it tells you which path to take: attach if the node is only detached, recover if it needs to be rebuilt.

All of this stays scriptable. --yes only skips the plain yes/no prompt. A typed confirmation has to be given explicitly with --confirm <token>, and a NO-GO can only be overridden with --force together with the token. --read-only disables every control command for the session, and --ticket records your change ticket in the audit log.

Configuration as a transaction

pgpool configuration is spread over four files that must be identical on every pgpool host, and parameters differ in whether they take effect on reload or need a restart. poolwarden treats a configuration change as a staged transaction across the whole cluster.

sequenceDiagram autonumber participant D as DBA participant PW as poolwarden participant A as pgpool host A participant B as pgpool host B D->>PW: config set num_init_children 48 PW->>PW: parse pgpool.conf (round-trip, comments kept)
stage in /var/lib/poolwarden/staged.json D->>PW: config diff PW-->>D: file vs staged vs live value, context = restart D->>PW: config validate PW->>PW: type/range/enum checks, CONN_BUDGET, drift check across hosts D->>PW: config apply PW->>A: lock cluster, back up (version 17), write atomically PW->>B: back up (version 17), write atomically PW->>B: systemctl restart pgpool-II (standby first) PW->>B: verify live: PGPOOL SHOW num_init_children = 48 PW->>A: systemctl restart pgpool-II (leader last) PW->>A: verify live value PW-->>D: per-host table, outcome success, audit event Note over PW,B: if any host fails: restore version 17 on every host already touched,
exit 5 (rolled back) or exit 6 (manual intervention)

set, diff, validate, apply. Restart class changes restart the standby first and the watchdog leader last, and a failure rolls back every host that was touched.

A few pieces make this work:

  • Round-trip parsers. internal/pgconf parses pgpool.conf, pool_hba.conf, pcp.conf and pool_passwd into structures that write back byte for byte identical when nothing has changed. Your comments and layout survive, and the diff you see is the diff you get.
  • A parameter catalogue for pgpool 4.4 and 4.5 with the type, allowed values and whether a change is reload or restart class. Any parameter whose context I could not confirm against the documentation is flagged Unverified and treated as restart class, which is the safe default.
  • Validation as a gate. config apply does not proceed past a failed validate. The connection budget check (num_init_children × max_pool against max_connections) is a warning you have to acknowledge.
  • Versioned backups and rollback. Every apply keeps the previous files under a version number. config rollback <version> restores them on all hosts and reloads or restarts depending on what the restored values need.
  • The same flow for the other files. hba add/remove, pcpuser add/remove, pooluser add/remove (md5 and scram are computed in process, since pg_md5 wants a TTY) and backend add/remove/set all go through the same staging and apply.

Each entry is hash chained to the one before it and copied to syslog. audit verify catches an edited, deleted or reordered line.

Each control command produces two entries, requested and finished, with the full pre-flight verdict, the plan, the per host step timings, the diff for configuration changes, the outcome (success, failed, rolled_back, aborted or refused) and the exit code. Secrets are masked before anything is written. sql queries and shell session start and end are logged too, and read-only commands can be logged if you turn that on. audit show, audit search and audit verify read it all back.

Working with it

poolwarden is one cobra command tree used in three ways. poolwarden status runs once and exits with a meaningful code. poolwarden on its own opens a shell whose prompt tells you where you are, pgpool[prod@db1]> or pgpool[prod@db1 DEGRADED]>, with tab completion driven from the same command tree (node ids, hosts, parameter names and finding ids complete from live data), history per operator, and a Ctrl-C that cancels the running command instead of killing the shell. watch and top give you full screen live views.

ExitMeaningExitMeaning
0ok5apply failed, rolled back
1usage6apply and rollback both failed

4validation failed--nagiosmaps to 0/1/2/3 with one summary line

Every error is three lines, error:, cause: and next:, and the last one is a command you can paste. An unknown SSH host key gives you the exact ssh-keyscan -H line. An unsafe config permission gives you the chmod.

Setup is poolwarden init. It finds the local pgpool, reads backend_hostnameN and the watchdog peers out of pgpool.conf, probes each host, and writes /etc/poolwarden.yaml. The YAML describes what each host is (roles, addresses, paths), never what state it is in. There is no primary: field, so a failover never means a config change.

What a failover looks like through it

I exercised the tool end to end on two Docker clusters running pgpool-II 4.5.13 and PostgreSQL 18: a two host layout with pgpool and PostgreSQL on the same machines, and a four host layout with them split. The scenario suite covered failover, online recovery, switchover and failback, detach and attach, loss of the watchdog leader with the VIP moving, configuration transactions and audit verification, and it passed on both. The step by step report with the captured logs is in the repository. Here I only want to show the shape of the failover and failback cycle as poolwarden sees it.

sequenceDiagram autonumber participant P0 as node 0 (primary) participant PP as pgpool-II participant P1 as node 1 (standby) participant PW as poolwarden Note over P0: primary crashes PP->>P0: health check fails 3 times PP->>PP: watchdog consensus, then failover_command PP->>P1: promote (timeline 1 to 2) PP->>P0: follow_primary_command: re-point to node 1 PW->>PP: nodes / diagnose PW-->>PW: node 1 primary, node 0 down, NODE_DOWN
FAILOVER lines in logs, nothing to do in the YAML Note over PW,P0: Failback part 1: rebuild the old primary PW->>PP: recover 0 (pre-flight: recovery script present, node down) PP->>P1: pgpool_recovery, pg_basebackup -R, pgpool_remote_start P0-->>P1: walreceiver streaming on timeline 2 PW-->>PW: verify: node 0 standby, up, streaming Note over PW,P1: Failback part 2: switch the primary back PW->>PP: promote 0 (pre-flight: node 0 most advanced, quorum, no split brain) PP->>P0: pcp_promote_node -s, promote (timeline 2 to 3) PP->>P1: follow_primary_command: pg_rewind or re-point to node 0 PW-->>PW: verify new primary, then verify old primary rejoined and streaming

The automatic failover is pgpool's job. poolwarden shows you what happened and turns the two step failback (recover, then switchover) into a guarded, verified and audited operation.

A word of caution. All of this testing was done in a pure Docker environment, with a container for every pgpool and PostgreSQL node and a small svc script standing in for systemctl. The tool only uses standard interfaces (SQL, PCP, SSH, systemctl, ip), so I expect it to work as it is on VMs and bare metal, but I have not run it there yet. Treat the control and configuration commands with the same care you would give any new tool on a production cluster. Start with the read-only side and keep --read-only on until you have watched it behave on your own hosts.

Running against a real cluster instead of fixtures also turned up a handful of bugs that no unit test would have caught: matching standbys when application_name is walreceiver, a global 20 second deadline that cut recover off in the middle of a basebackup, a stale timeline source in the attach pre-flight, and reload verification racing pgpool's asynchronous reload. They are all fixed and written up in the test report, which is worth a read if you want the timestamped pgpool and PostgreSQL logs behind each step.

The principles behind it

  • A wrapper, not a replacement. Only pgpool's and PostgreSQL's own interfaces, never a shell, never pg_promote().
  • One snapshot, many consumers. Views, rules, forecasts and pre-flights are pure functions over the same data, so they cannot contradict each other.
  • Never hang. Every source has a deadline. Partial information is shown as partial, with a finding that says why.
  • Check first, confirm, verify after. No control action runs without a checklist before it and a state check after it.
  • Changes are transactions. Staged, validated, backed up, applied in a safe order, and rolled back as a unit.
  • Every action has a name on it. Identity comes from the SSH key rather than the shared OS account, and the hash chain can be verified.
  • A static binary and no daemon. CGO_ENABLED=0, linux/amd64 and arm64, man pages, RPM and deb. Its footprint is /etc/poolwarden.yaml and /var/lib/poolwarden.

Try it

git clone https://github.com/rameshsraj/poolwarden
cd poolwarden && make build          # bin/poolwarden
sudo bin/poolwarden init             # detects pgpool, writes /etc/poolwarden.yaml
poolwarden status                    # one shot
poolwarden diagnose                  # what, why, and what to run next
poolwarden                           # interactive shell
It is safe to install and try on a production cluster. poolwarden is a wrapper, not a service: there is no daemon, no proxy and nothing in the client traffic path. The monitoring and diagnosis commands (status, nodes, lag, watchdog, diagnose, forecast, errors, logs and the rest) only read, using the same SHOW POOL_*, pcp_*_info and pg_stat_* calls you already run by hand. With --read-only every control and configuration command is disabled, so you can point it at a live cluster and get the cross checked views and findings with no way of changing anything. Turn on the control side once you are comfortable with what it shows you.

The repository holds the design and functional specifications, the implementation decisions log, an operator guide, the Docker test bed for both layouts, and the full test report with captured logs.

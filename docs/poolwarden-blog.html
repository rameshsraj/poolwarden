poolwarden: a command center for pgpool-II

One binary, one terminal, one pgpool cluster — see it, understand it, change it safely, and prove who did what.

Go · pgpool-II 4.4/4.5 · PostgreSQL 14+ · Source: github.com/rameshsraj/poolwarden

If you run PostgreSQL behind pgpool-II with streaming replication, you know the drill when something looks off. You open four terminals: one for psql -p 9999 and SHOW POOL_NODES, one for pcp_watchdog_info, one to log into each backend and run pg_is_in_recovery() and pg_stat_replication, and one to tail logs on whichever host you suspect. Then you reconcile the four views in your head, decide whether to run pcp_promote_node, and hope you typed the right node id.

poolwarden is the tool I wanted in that moment. It is a single static Go binary that a DBA runs over SSH on a pgpool host. It is not a proxy, not an agent and not a daemon — it is a thin, careful layer over the interfaces pgpool and PostgreSQL already expose, with the judgment, guard-rails and record-keeping that those interfaces lack.

Why another tool?

pgpool-II is excellent at what it does: pooling, load balancing, health checks, automatic failover and watchdog-managed virtual IPs. What it leaves to the operator is operating it, and that part has four recurring pain points.

Four sources of truth that disagree

pgpool's SHOW POOL_NODES says what pgpool believes. Each PostgreSQL node knows what it actually is. The watchdog knows who holds the VIP. These drift apart precisely when things go wrong, and nothing correlates them for you.

Powerful commands with no seat belt

pcp_promote_node, pcp_detach_node and pcp_recovery_node execute immediately. No pre-flight checks (is this standby even caught up?), no confirmation, no verification afterwards, no record of who ran it.

Configuration by hand on N hosts

pgpool.conf, pool_hba.conf, pcp.conf and pool_passwd must be identical on every pgpool host. Editing them by hand means drift, and discovering the drift during the next failover.

A shared account and scattered logs

Everyone logs in as postgres, so "who restarted pgpool at 02:14?" has no answer. pgpool and PostgreSQL logs live on different hosts in different formats.

poolwarden addresses each of these directly: cross-checked views, guarded control, transactional configuration and an identity-resolving audit log.

Where it sits

The most important design decision is what poolwarden is not. It is not in the client traffic path, it never talks to application clients, and it never bypasses pgpool to control PostgreSQL. Delete the binary and the cluster keeps running exactly as before.

Architecture

Internally poolwarden is a layered pipeline. Everything the user sees — a table, a finding, a plan — is derived from a single immutable Snapshot that one component builds and every other component reads.

The collector and the Snapshot

Every command starts the same way: the collector fans out to all sources in parallel, each with its own deadline (default 3 s), and assembles whatever came back into a Snapshot. A source that times out is recorded as UNREACHABLE and never blocks the others — a dead backend costs you three seconds, not a hung terminal. The snapshot also carries the provenance of each fact, so a view can show "pgpool says up, direct connection says refused" rather than silently picking one.

One collection, many consumers. Degraded mode kicks in when pgpool itself cannot answer SQL — the very moment you most need to see the cluster.

Degraded mode deserves a note. The classic pgpool outage is "all children busy": pgpool is alive but your psql -p 9999 hangs forever. poolwarden detects the hang, switches node state to pcp_node_info and backend state to direct connections, and marks the output DEGRADED. You still get a picture of the cluster, plus a finding telling you why it is partial.

Diagnosis: findings with evidence and a next step

The diagnosis engine is a catalogue of 29 rules. Each is a pure function func(Snapshot, History, Config) []Finding — no I/O, trivially table-tested — and each finding carries a severity, the subject it applies to, the evidence that fired it, the likely cause, and the exact next command to run.

Forecasting

The collector writes every snapshot to a 24-hour on-disk ring. forecast runs a linear regression over the last five minutes of lag, retained WAL and busy children, and reports slope, R² and an ETA to the critical threshold — but only when R² ≥ 0.6; a noisy series is reported as unstable rather than given a fake ETA. Those same trends feed the rising-lag rule and the per-node health score shown in status.

Guarded node control

This is where the tool earns its name. Every control command — promote, detach, attach, recover, reload — runs the same five-phase flow, and every phase is timed and audited.

Pre-flight → plan → confirm → execute → verify. Refusals and aborts are recorded just like successes.

The pre-flight checklists are specific to each action. For a switchover, poolwarden checks that the target is a standby and up, that its replay delay is under the warning threshold, that it holds the most advanced LSN of all standbys, that watchdog quorum exists, that failover_command and follow_primary_command are set, that there is no split-brain and no failover already in flight. detach warns you when the target is the primary (because that triggers a failover) and tells you how much load-balancing capacity you are about to lose. attach refuses a node that is on a different timeline from the primary — the classic way to attach a stale node and corrupt your read traffic.

The output is a timeline, not a spinner:

$ poolwarden promote 0 --ticket TB-1
STEP                         START     END       DURATION  RESULT
preflight                    05:28:25  05:28:25  0.1s      ok
pcp_promote_node             05:28:25  05:28:25  0.0s      ok
verify                       05:28:25  05:28:27  2s        ok
verify (old primary rejoin)  05:28:27  05:28:28  0.1s
outcome: success  event: d3c47530ebb20ec0

Note the second verify step. A switchover is not finished when the new primary accepts writes; it is finished when the old primary has been re-pointed by follow_primary_command and is streaming again. poolwarden waits for that too, and if the old primary does not come back it tells you which recovery path applies (attach if it is merely detached, recover if it needs a rebuild).

Scriptable without losing the guard-rails. --yes only skips the plain yes/no prompt. A typed confirmation can only be supplied explicitly with --confirm <token>, and a NO-GO can only be overridden with --force plus the token. --read-only disables every control command for the session, and --ticket ties the change to your change-management record in the audit log.

Configuration as a transaction

pgpool configuration spans four files that must be identical on every pgpool host, and parameters differ in whether they take effect on reload or need a restart. poolwarden models a configuration change as a staged transaction across the whole cluster.

sequenceDiagram autonumber participant D as DBA participant PW as poolwarden participant A as pgpool host A participant B as pgpool host B D->>PW: config set num_init_children 48 PW->>PW: parse pgpool.conf (round-trip, comments kept)
stage in /var/lib/poolwarden/staged.json D->>PW: config diff PW-->>D: file vs staged vs live value, context = restart D->>PW: config validate PW->>PW: type/range/enum checks, CONN_BUDGET, drift check across hosts D->>PW: config apply PW->>A: lock cluster, back up (version 17), write atomically PW->>B: back up (version 17), write atomically PW->>B: systemctl restart pgpool-II (standby first) PW->>B: verify live: PGPOOL SHOW num_init_children = 48 PW->>A: systemctl restart pgpool-II (leader last) PW->>A: verify live value PW-->>D: per-host table, outcome success, audit event Note over PW,B: if any host fails: restore version 17 on every host already touched,
exit 5 (rolled back) or exit 6 (manual intervention)

set → diff → validate → apply. Restart-class changes restart the standby first and the watchdog leader last; failures roll every touched host back.

The pieces that make this work:

  • Round-trip parsers. internal/pgconf parses pgpool.conf, pool_hba.conf, pcp.conf and pool_passwd into structures that write back byte-identical when nothing has changed. Your comments and layout survive; the diff you see is the diff you get.
  • A parameter catalogue for pgpool 4.4 and 4.5: type, allowed values, and whether a change is reload or restart class. Any parameter whose context could not be verified against the docs is flagged Unverified and treated as restart-class, the safe default.
  • Validation as a gate. config apply will not proceed past a failed validate; the connection-budget check (num_init_children × max_pool vs. max_connections) is a warning you must acknowledge.
  • Versioned backups and rollback. Every apply stores the previous files under a version number. config rollback <version> restores them on all hosts and reloads or restarts as the restored values require.
  • The same flow for the other files. hba add/remove, pcpuser add/remove, pooluser add/remove (md5/scram computed in-process — pg_md5 needs a TTY) and backend add/remove/set all stage through the same transaction.

An audit log that knows who you are

On most database hosts everyone is postgres or root, so an audit log that records the OS user records nothing useful. poolwarden resolves identity from every signal available at the moment of the command and stores all of them:

Every entry is hash-chained to the previous one and mirrored to syslog; audit verify detects an edited, deleted or reordered line.

Each control command produces two entries, requested and finished, with the full pre-flight verdict, the plan, the per-host step timings, the diff for configuration changes, the outcome (success, failed, rolled_back, aborted or refused) and the exit code. Secrets are masked before writing. sql queries, shell session start/end and — optionally — read-only commands are logged too. audit show, audit search and audit verify read it back.

The operator experience

poolwarden is one cobra command tree used three ways. poolwarden status runs once and exits with a meaningful code. poolwarden alone opens a shell whose prompt tells you where you are — pgpool[prod@db1]>, or pgpool[prod@db1 DEGRADED]> — with tab completion driven from the same command tree (node ids, hosts, parameter names and finding ids complete live), per-operator history, and Ctrl-C that cancels the running command rather than the shell. watch and top give full-screen live views.

ExitMeaningExitMeaning
0ok5apply failed, rolled back
1usage6apply and rollback both failed

4validation failed--nagiosmaps to 0/1/2/3 with one summary line

Every error is three lines — error:, cause:, next: — and the last line is a command you can paste. An unknown SSH host key gives you the exact ssh-keyscan -H line; an unsafe config permission gives you the chmod.

Setup is poolwarden init: it detects the local pgpool, reads backend_hostnameN and the watchdog peers out of pgpool.conf, probes each host, and writes /etc/poolwarden.yaml. The YAML describes what each host is (roles, addresses, paths), never what state it is in — there is no primary: field, so a failover never requires a config change.

What a failover looks like through it

The tool was exercised end to end on two Docker clusters (pgpool-II 4.5.13, PostgreSQL 18): a two-host layout with pgpool and PostgreSQL co-located, and a four-host layout with them split. The full scenario suite — failover, online recovery, switchover and failback, detach/attach, watchdog leader loss with VIP move, configuration transactions, audit verification — passed on both. The detailed, capture-by-capture report lives in the repository; here is just the shape of the failover and failback cycle as poolwarden sees it.

sequenceDiagram autonumber participant P0 as node 0 (primary) participant PP as pgpool-II participant P1 as node 1 (standby) participant PW as poolwarden Note over P0: primary crashes PP->>P0: health check ×3 fails PP->>PP: watchdog consensus → failover_command PP->>P1: promote (timeline 1 → 2) PP->>P0: follow_primary_command: re-point to node 1 PW->>PP: nodes / diagnose PW-->>PW: node 1 primary · node 0 down · NODE_DOWN
FAILOVER lines in logs · nothing to do in the YAML Note over PW,P0: Failback part 1 — rebuild the old primary PW->>PP: recover 0 (pre-flight: recovery script present, node down) PP->>P1: pgpool_recovery → pg_basebackup -R → pgpool_remote_start P0-->>P1: walreceiver streaming on timeline 2 PW-->>PW: verify: node 0 standby, up, streaming Note over PW,P1: Failback part 2 — switch the primary back PW->>PP: promote 0 (pre-flight: node 0 most advanced, quorum, no split-brain) PP->>P0: pcp_promote_node -s → promote (timeline 2 → 3) PP->>P1: follow_primary_command: pg_rewind / re-point to node 0 PW-->>PW: verify new primary, then verify old primary rejoined and streaming

Automatic failover is pgpool's job; poolwarden shows you what happened and makes the two-step failback (recover, then switchover) a guarded, verified, audited operation.

Tested in Docker. Everything above ran in a pure Docker environment — containers for every pgpool and PostgreSQL node, with a svc stand-in for systemctl. The tool uses only standard interfaces (SQL, PCP, SSH, systemctl, ip), so it is expected to work as is on VMs and bare metal, but that has not yet been exercised there. Treat the control and configuration commands with the caution you would give any new tool on a production cluster: start with the read-only side, and use --read-only until you have seen it behave on your own hosts.

Running the tool against a real cluster rather than fixtures also found a batch of bugs that no unit test would have: standby matching when application_name is walreceiver, a global 20-second deadline that cut recover off mid-basebackup, a stale timeline source in the attach pre-flight, and reload verification racing pgpool's asynchronous reload. All are fixed and covered in the repository's test report, which is worth reading if you want the timestamped pgpool and PostgreSQL logs behind each step.

Design principles, in short

  • Wrapper, not replacement. Only pgpool's and PostgreSQL's own interfaces; never a shell, never pg_promote().
  • One snapshot, many consumers. Views, rules, forecasts and pre-flights are pure functions over the same data, so they cannot disagree with each other.
  • Never hang. Every source has a deadline; partial information is shown as partial, with a finding explaining why.
  • Pre-flight, confirm, verify. No control action runs without a checklist before and a state check after.
  • Changes are transactions. Staged, validated, backed up, applied in a safe order, rolled back as a unit.
  • Every action is attributable. Identity from the SSH key, not the shared OS account; a hash chain you can verify.
  • Static binary, no daemon. CGO_ENABLED=0, linux/amd64 and arm64, man pages, RPM/deb. Footprint: /etc/poolwarden.yaml and /var/lib/poolwarden.

Try it

git clone https://github.com/rameshsraj/poolwarden
cd poolwarden && make build          # bin/poolwarden
sudo bin/poolwarden init             # detects pgpool, writes /etc/poolwarden.yaml
poolwarden status                    # one shot
poolwarden diagnose                  # what, why, and what to run next
poolwarden                           # interactive shell
Safe to install and try in production. poolwarden is a wrapper, not a service: it has no daemon, no proxy and no presence in the client traffic path, and the monitoring and diagnosis commands (status, nodes, lag, watchdog, diagnose, forecast, errors, logs, …) only read — the same SHOW POOL_*, pcp_*_info and pg_stat_* calls you already run by hand. Run it with --read-only and every control and configuration command is disabled, so you can configure it against a live cluster and get the cross-checked views and findings without any possibility of changing state. Enable the control side only once you are comfortable with what it shows you.

The repository contains the design and functional specifications, the implementation decisions log, an operator guide, a Docker test bed for both layouts, and the full test report with captured logs.

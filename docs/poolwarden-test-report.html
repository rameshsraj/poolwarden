3. What poolwarden is and where it sits

poolwarden is a single-binary operator tool for pgpool-II HA clusters. It never touches PostgreSQL control commands (pg_ctl promote, pg_rewind) itself; every control action goes through pgpool's own interfaces: the PCP commands (pcp_promote_node, pcp_detach_node, pcp_attach_node, pcp_recovery_node, pcp_reload_config, pcp_watchdog_info) and pgpool's SQL protocol commands (SHOW POOL_NODES, SHOW POOL_HEALTH_CHECK_STATS, etc.). pgpool then runs its configured failover_command/follow_primary_command/recovery_* scripts, which are the ones doing pg_ctl/ssh work. poolwarden adds what pgpool lacks: pre-flight safety checks, confirmations with typed tokens, audit trail with hash-chained entries, a diagnosis engine, config-file transaction (diff/validate/apply/rollback), log classification, and per-host file/ssh orchestration.

Test-bed shortcuts (lab-only, not production practice)

  • pgpool runs as root (container) so its scripts can ssh and run ip addr; a shared throwaway keypair baked at build time gives root+postgres passwordless ssh; known_hosts is pre-seeded by keyscan.
  • A svc stand-in emulates systemctl for restart-class config applies (no systemd in containers).
  • Passwords are pgpool everywhere, md5; the VIP lives inside the compose subnet (no real ARP broadcast reach).
  • PostgreSQL log files live inside PGDATA/log and are copied by pg_basebackup/pg_rewind, so a node's PG log can contain lines that originated on the other node. Per-node attribution below relies on the pgpool event logs and the poolwarden captures.

5. How replication works in this cluster

Streaming replication is PostgreSQL-native: the standby connects to the primary over primary_conninfo (host/port/user, from pg_basebackup -R which also writes standby.signal), a walreceiver on the standby streams WAL from a walsender on the primary and replays it. The primary sees the standby in pg_stat_replication (one row per walsender: application_name=walreceiver, client_addr, state=streaming); the standby reports itself in pg_stat_wal_receiver (status, received_tli = the timeline it is receiving). The control file's timeline_id on a standby is only the last restartpoint's TL and lags after rewind/failover; the live TL comes from received_tli (this was poolwarden bug Q).
